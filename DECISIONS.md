1. **Indexes.** For employees, unique `emp_code` supports identity/lookups; `(department, emp_code)` supports filtered lists; `joined_on` supports headcount. For logs, unique `(emp_code, date)` enforces one record per employee/day; `(date desc, emp_code)` supports ordered lists and month scans. I rejected a `status` index: five low-selectivity values add write cost.
2. **Punch-in race.** Both requests may read the employee and build the same document, then call `insert_one`. The unique `(emp_code, date)` index permits one insert; MongoDB rejects the other with `DuplicateKeyError`, returned as 409. No preliminary attendance lookup is used.
3. **Ties.** `$rank` gives tied employees the same competition rank. Filtering with `rank <= limit` after ranking returns every employee tied at the cutoff, even if this exceeds `limit`; output ties are ordered by `emp_code`.
4. **Headcount.** The department-summary pipeline starts with employees who joined by month end, then looks up each employee's attendance. An empty lookup is preserved during unwind, so employees without logs still contribute to headcount.
5. **100x data.** I would maintain daily employee summaries with attendance writes so analytics scan fewer documents. I would also remove the large employee-code `$in` list from the department trend query.
